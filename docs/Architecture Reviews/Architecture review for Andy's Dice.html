Andy's Dice: deepening opportunities

Scope came from the commit history. The busiest files are in the app module's Roll path: Skeleton (17 commits), AndysDice (14), RollSession (12) and RollController (11). Next is render's DiceScene (10). Persistence was reviewed too and is already deep, so it has no card.

Deepen the Roll lifecycle into one module

Strong in-process
  • app/RollController.java (status, underWay, playing, abandoned)
  • app/RollQueue.java (queued, startsAt=NaN, closed)
  • app/RollSession.java:110-141 (pulse policy, failure fan-out)
  • app/RollUi.java:70 (failed)
  • app/FastForward.java:61,143 (second clock-speed owner)
  • app/Bench.java:247 · Skeleton.java:133 (idle rule, copies 2 and 3)

Before: five clock listeners whose order is set by construction order

After: one listener, one state machine

roll(expr, savedName?) cancelQueued() abandon()

Roll lifecycle

Ready→ Pre-simulating→ Playing→ Revealed→ Beat (Queued Roll) Failed Roll Abandoned

Hidden inside: queue beat, listener order, the one idle rule, the parse.

onEvent(RollStatus | Queued) needsClock()

Problem

A Roll's state is held in about six classes and kept in step by callbacks plus the order clock listeners were registered in. Two recent fixes patched exactly that: 0d9ce4b (abandoned flag) and 86e0b04 (Esc).

Solution

Merge the controller, the Queued Roll and the pulse/idle rule into one module that registers a single clock listener and exposes a small event stream. RollSession keeps only the wiring of the view.

Wins

  • Locality: listener order internal
  • One idle rule, not three
  • "Failed session" held once
  • QueuedRollTest + RollControllerTest share one interface
  • Bench stops polling internals

The physics side is already a seam with two adapters (PhysicsJobs: the worker in production, HeldPhysics in tests), so the deepened module stays testable without GL or Jolt.

Strong in-process likely bug

Before: physics, render and sound each fetch "the Tray" at a different moment

After: the Tray is part of the Roll

all read the Tray from the Roll; the redraw waits for the next Roll or happens when idle

Problem

Nothing records which Tray a Roll was planned in, and the Look tab stays live during a Roll. From reading the code, a mid-Roll pick draws and sounds a chain that was simulated in a different Tray. This hasn't been reproduced at runtime.

Solution

Capture the Tray (and Look) when the Roll is planned and carry it in the plan or chain. Physics, the GL Tray and sound read it from there. The per-Throw thrown kinds go there too (computed today in both Clatter:119 and ChainPlayback:75).

Wins

  • One fact, one source
  • Drop Clatter's Tray supplier
  • Mid-Roll Look test becomes trivial
  • Kinds-per-Throw computed once

One frame hand-over for DiceScene

Worth exploring in-process

  • app/Skeleton.java:226-231, 348-363 (requestFrame ×3, panSound ×2)

Before: nine setters, three atomicity rules, and a frame request each caller must remember

After: publish one immutable snapshot of the frame

DiceScene

publish is atomic and schedules the frame itself

shadowtraycopydice

The projection is exposed once, so CameraPanning stops copying it.

Problem

DiceScene's implementation is deep but its interface is a grab-bag. setLook can tear across a frame, and each caller must remember requestFrame. The Look triple is spelled out three times.

Solution

Replace the setters with a single snapshot publish that also requests the frame. Gallery and GpuBench build snapshots instead of calling setters.

Wins

  • No torn Look frames
  • Interface: 9 setters → 1
  • Leverage: Gallery, GpuBench, GlTray
  • Snapshot assertable without GL
This fits ADR-0002's "messages to the render thread". Its Javadoc at RenderThread.java:148 already describes messages that, in today's code, are volatile setters.
